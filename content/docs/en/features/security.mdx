Your Securo instance holds your complete financial history, so the login deserves more than a password. Securo supports passkeys, TOTP two-factor authentication, and OIDC single sign-on, all self-hosted, with nothing leaving your server.

![Login and security](/screenshots/security.png)

## Passkeys

Passkeys let you sign in with your device's fingerprint reader, face unlock, or a hardware security key, no password typed. Register one from your account settings and the login page gains a **Continue with passkey** button; the browser also offers a saved passkey straight from the email field, the way it offers a saved password.

- You can register multiple passkeys (laptop, phone, a backup hardware key) and remove any of them later
- A passkey can also serve as the **second factor** for password logins, instead of an authenticator code
- Passkeys require a secure context: serve Securo over **HTTPS** (or use `localhost`). On a plain-HTTP LAN address the browser will refuse, that's a platform rule, not a Securo limitation
- By default Securo follows whatever address you open it on. To pin passkeys to one domain, set `WEBAUTHN_RP_ID` (use the parent domain if you reach Securo on several subdomains). Requests from an unusable address get an explanation in the UI instead of a silent failure

## Two-Factor Authentication

Add a time-based one-time code (TOTP) as a second step after your password:

1. Open your account settings and choose **Set Up Two-Factor Authentication**
2. Scan the QR code with any authenticator app (Aegis, Google Authenticator, 1Password, ...)
3. Confirm with a 6-digit code, and 2FA is on

Codes from the adjacent time windows are accepted, so an authenticator whose clock drifts a few seconds still works, and the verification endpoint is rate-limited against guessing. Disabling 2FA requires both your password and a current code.

## Single Sign-On (OIDC)

If you run an identity provider (Authelia, Authentik, Keycloak, or any OIDC-compliant service), Securo can delegate login to it. Enable it with environment variables:

```ini
OIDC_ENABLED=true
OIDC_PROVIDER_NAME=Authentik
OIDC_DISCOVERY_URL=https://auth.yourdomain.com/.well-known/openid-configuration
OIDC_CLIENT_ID=securo
OIDC_CLIENT_SECRET=your-client-secret
# Optional; defaults to ${FRONTEND_URL}/api/auth/oidc/callback
OIDC_REDIRECT_URI=https://your-securo-host/api/auth/oidc/callback
```

In your provider, register `https://your-securo-host/api/auth/oidc/callback` as the redirect URI. New users are auto-provisioned by default (`OIDC_AUTO_REGISTER=true`) using verified email addresses; set `OIDC_AUTO_REGISTER=false` to admit only existing Securo users whose email matches the provider claim.

The login page gains a "Continue with ..." button named after your provider. Auto-registration of new users, linking existing accounts, and provider role sync are covered in the sections below; see `.env.example` in the repository for the full list of `OIDC_*` options.

### Linking existing accounts

An account that already exists in Securo, created with a password, is never linked to an OIDC identity automatically. The first SSO login of such a user is rejected until you choose a linking policy with `OIDC_EXISTING_USER_LINK_MODE`:

| Value | Behavior |
|-------|----------|
| `disabled` (default) | Never link. Existing accounts keep using password login. |
| `verified_email` | Link the existing account when the provider sends `email_verified=true` for the same email. |
| `email` | Link on a matching email alone, even without `email_verified`. |

Use `verified_email` to move your existing users to SSO without recreating their accounts and data. Only pick `email` if you trust your provider to own every address it asserts, since anyone able to set an email there could claim the matching Securo account. An OIDC identity already linked to another account is always rejected, in every mode.

### OIDC Only

To make the identity provider the only way in, set `LOCAL_AUTH_ENABLED=false`. Password and passkey sign-in are switched off along with every local-auth route behind them, and the login page shows only the provider button. Securo refuses to start with this setting unless OIDC is enabled, so a typo cannot lock everyone out. Users who had enrolled 2FA or passkeys before the switch can still remove them from their account settings; they just cannot add new ones.

On a fresh OIDC-only instance, the first account must arrive through OIDC: keep `OIDC_AUTO_REGISTER=true`, enable `OIDC_SYNC_ROLES=true`, and make sure that identity's roles claim carries one of the `OIDC_ADMIN_ROLES` values, so the first login becomes a Securo administrator. Don't turn auto-registration off before at least one matching account exists.

### OIDC role sync

With `OIDC_SYNC_ROLES=true`, Securo maps the roles/groups your provider sends onto its own permissions on every OIDC login:

```ini
OIDC_SYNC_ROLES=true
OIDC_ROLES_CLAIM=groups            # the claim holding roles/groups; "groups" fits Authentik and Pocket ID
OIDC_ADMIN_ROLES=securo-admins     # membership grants or revokes Securo admin
OIDC_WORKSPACE_ROLE_MAP={"securo-owners":"owner","securo-editors":"editor","securo-viewers":"viewer"}
```

`OIDC_WORKSPACE_ROLE_MAP` maps provider roles to the user's Personal workspace role (`owner`, `editor`, or `viewer`); when several mapped roles are present, the highest permission wins. Leave `OIDC_SYNC_ROLES=false` to keep all Securo roles managed locally.

## Passwords

Password login is available whenever local auth is on. You can change your password from account settings, and workspace owners who create accounts for new members set only an initial password, which the member can change after their first login.
