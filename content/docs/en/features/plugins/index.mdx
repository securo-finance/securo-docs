Plugins bring ready-made categories, category groups and rules into a workspace. Someone who already sorted out how to categorize their pet shop, their country's supermarkets or their streaming services can publish it once, and you install it in a couple of clicks instead of rebuilding it by hand.

There are two kinds:

- **Data plugins** only add categories, groups and rules. They don't run code, don't change the interface and can't send anything anywhere
- **Plugins with code** connect a workspace to an outside service (a payment provider, an email account, a storage service). Their code runs on your server, isolated from Securo and your data, and only reaches the hosts it declares. They need an extra container; see [Plugins with code](#plugins-with-code)

## Enabling Plugins

Plugins are off by default. Set this in the backend environment and restart it:

```bash
PLUGINS_ENABLED=true
```

No extra container starts. While plugins are off, Securo never contacts the catalog and the plugin screens are hidden.

## Browsing the Catalog

Go to **Workspace settings**, find the **Plugins** section and click **Browse catalog**. The catalog lists every published plugin with its author, what it brings (for example "2 categories, 5 rules"), its languages and its GitHub stars.

- **All**, **Trending** and **New** switch between the full list, the plugins gaining stars fastest relative to their size, and those added in the last 30 days
- Search by name, author, description or topic, and filter by type, content, language or status (installed, updates available)
- Sort by popularity, trend, last update, newest or name

Click a plugin to open its page: the author's README, and under **What's inside** every category, group and rule it would add, with each rule's conditions and actions spelled out.

Plugins are not reviewed by the Securo team. That's why the preview below exists, and why it's worth reading.

## Installing

Click **Install**. Before anything happens, Securo shows exactly what changes in this workspace:

- **Adds**: the categories, groups and rules that will be created
- **Skips ... you already have**: a category with the same name as one of yours isn't duplicated; the plugin's rules use yours
- **Also creates default categories its rules need**: when a rule points at a built-in category you deleted

Nothing is applied until you confirm. Your existing transactions keep the categories they already have; the plugin's rules apply to new transactions, or to old ones when you [re-apply your rules](/docs/features/rules#re-applying-rules).

If something changes in the workspace or the catalog while the preview is open, confirming fails safely and asks you to review it again.

Only members who can edit the workspace can install, update or remove plugins. Viewers can browse the catalog.

## Updating

When the author publishes a new version, the plugin shows **Update available** in the catalog. Open it and click **Update**. The update preview works like the install one, and adds what happens to what you've changed:

- Items you **edited** (renamed a category, changed a rule) are **left as they are**. Your edit always wins
- Items the plugin no longer ships are **deleted**, unless you edited them or they're still in use, in which case they're **handed over to you** and become ordinary categories and rules

A plugin that needs a newer Securo shows **Needs Securo x.y.z** instead of offering the update.

## Removing

In **Workspace settings**, the **Plugins** section lists what's installed in the workspace, with its version. Click the trash icon next to a plugin to remove it. The preview lists what goes and what stays:

- Rules and categories you never touched are deleted
- Anything you edited, and any category still used by transactions, budgets, recurring transactions or your own rules, is **handed over to you** and stays exactly as it is

Removing always works, even if the plugin was later revoked or the catalog can't be reached.

## Revoked Plugins

A plugin found to be harmful or broken can be revoked in the catalog. It can no longer be installed or updated, and shows **Revoked** with the reason. Workspaces that already have it can still remove it.

## Plugins with Code

A plugin with code adds **integrations**: connections to outside services that Securo syncs on a schedule. Its code never runs inside Securo. It runs in a separate container, the **plugin runner**, under its own user, with no access to Securo's database, settings or secrets, and it can only reach the internet hosts it declares.

### Enabling the Runner

Plugins with code need, on top of `PLUGINS_ENABLED=true`:

- Two extra containers, started with the `plugins` profile: `docker compose --profile plugins up -d` (or add `plugins` to `COMPOSE_PROFILES`)
- In the backend environment:

```bash
PLUGINS_RUNNER_URL=http://plugins-runner:8090
# Long random values, for example from `openssl rand -hex 32`
PLUGINS_RUNNER_TOKEN=...
PLUGINS_EGRESS_SECRET=...
```

`plugins-runner` runs the plugins and `plugins-egress` is their only way out to the internet. Without them, plugins with code show as unavailable in the catalog and everything else keeps working.

### Installing

Only the workspace **owner** can install, update or remove a plugin with code. Before you confirm, the preview shows:

- A warning that the plugin runs code that isn't reviewed by the Securo team
- **Reaches**: every internet host the code may contact, each with the author's reason. With none, nothing leaves your server
- **Uses in this workspace**: what it may read or change in Securo (for example "Read and change transactions"), each with the author's reason

An update marks the hosts and permissions the new version adds, so you see exactly what you're agreeing to. Securo installs the code only from the catalog's copy, after checking its checksum. Each workspace runs the version its owner approved.

### Connections

After installing, open the plugin's page and go to the **Connections** tab. Members who can edit the workspace can:

- **Add a connection**: fill in what the service gave you (an API key, say). Secret fields are stored encrypted and are never shown again. For services you sign in to, Securo shows the return address to register with the service, then sends you there to sign in
- **Sync now**, or let Securo sync on the plugin's schedule. A failing connection is retried less often until it works again
- **Sign in again** when the service asks for it
- **Remove** a connection: its saved keys and access are deleted, and what it already brought in stays

Viewers see the connections and their status, never their keys.

### What the Code Can and Can't Do

- It reaches only the hosts it declared, and never an address inside your network
- When it declared what it uses in the workspace, each connection gets an access token limited to exactly that, revoked when the connection or the plugin is removed
- It sees only its own connections' settings and keys, never another plugin's
- Each run has time, memory and process limits, and nothing it starts outlives the run

Removing the plugin deletes its connections and their keys, revokes their tokens and removes its code from your server once no workspace uses it. An update to a version without code does the same, and the preview says so.

## Privacy

- Securo downloads the catalog only when someone opens it, and a plugin's files only when you open or install that plugin
- Every file is checked against the checksum the catalog lists before it's used
- Nothing about your workspace is sent: there's no account, no install counter and no telemetry. Popularity comes from GitHub stars
- Your server only ever talks to the catalog host, never to GitHub
- A plugin with code talks to the hosts it declared, which the preview lists before you install it; data plugins talk to nothing

You can point Securo at a mirror or your own catalog with `PLUGINS_INDEX_URL` (default `https://plugins.usesecuro.com/v1/index.json`).
