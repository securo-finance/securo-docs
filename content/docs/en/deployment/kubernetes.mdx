Securo ships an official Helm chart, published as an OCI artifact on GitHub Container Registry and listed on [Artifact Hub](https://artifacthub.io/packages/helm/securo/securo). Each release of the chart pins the Securo images from that same release, so a given chart version always deploys a known, matching application version.

## Install

No repository to add, install straight from the OCI registry:

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.domain=securo.yourdomain.com \
  --set secret.secretKey="$(openssl rand -hex 32)"
```

Check [the releases page](https://github.com/securo-finance/securo/releases) for the latest version number, chart versions track application versions.

## What the Chart Deploys

- **Backend** (FastAPI) and a database migration Job that the other pods wait for
- **Frontend** (nginx serving the built app, proxying `/api` to the backend)
- **Celery worker and beat** for background jobs
- **PostgreSQL** and **Redis**, bundled and enabled by default
- Optional **MCP server** for the AI agents feature, disabled by default
- Optional **plugin runner** and **egress proxy** for [plugins with code](/docs/features/plugins#plugins-with-code), disabled by default

Persistence is enabled by default for the database, attachments, and the agents knowledge base.

## Key Values

| Value | Default | Purpose |
| --- | --- | --- |
| `global.domain` | `securo.local` | Public domain of the app; OAuth callback URLs are derived from it |
| `global.tls` | `false` | Whether derived URLs use `https://` |
| `secret.secretKey` | empty | Signs sign-in tokens and encrypts saved credentials. Left empty, Securo generates a unique key on the first start and keeps it in the database; set your own to manage it yourself |
| `ingress.enabled` | `false` | Create an Ingress; `/api` is routed straight to the backend, everything else to the frontend |
| `httpRoute.enabled` | `false` | Gateway API HTTPRoute, as an alternative to Ingress, with the same `/api` split |
| `frontend.backendUrl` | derived | Where the frontend's nginx proxies `/api`. Defaults to the backend service's fully qualified name (`<release>-backend.<namespace>.svc.cluster.local`); override for a non-standard cluster domain |
| `persistence.*` | `enabled` | PVCs for database, attachments, agents knowledge |
| `config.storageProvider` | `"local"` | `s3` keeps attachments in an S3-compatible bucket instead of the attachments PVC; see [Kubernetes (Helm) Production](/docs/deployment/kubernetes-prod#s3-compatible-object-storage) |
| `config.trustedProxyHops` | `"1"` | Proxies whose `X-Forwarded-For` the backend trusts to find the visitor's address for rate limits. The Ingress controller or gateway is the one hop; add one per layer in front of it that appends to the header, such as a cloud load balancer. At `0` every visitor shares one login and register limit. Charts before this default left it at `0` |
| `config.agentsEnabled` | `"false"` | Optional AI agents feature |
| `mcpServer.publicRoute` | `false` | Adds `/mcp` to the Ingress or HTTPRoute so external MCP clients can reach the agents' MCP server. Set `config.agentsExternalMcpUrl` to the public URL with it |
| `plugins.runner.enabled` | `false` | Runs plugins with code: creates the plugin runner, its egress proxy, a NetworkPolicy and a Secret with a random runner token and egress secret. Turns `PLUGINS_ENABLED` on. See [Plugins With Code](/docs/deployment/kubernetes-prod#plugins-with-code) |
| `postgresql.enabled` / `redis.enabled` | `true` | Disable to bring your own database or Redis |

Optional integrations (bank sync, exchange rates, OIDC) take the same settings documented in the [Docker guide](/docs/deployment/docker), exposed as `secret.*` and `config.*` values. Inspect the full annotated list for your version with:

```bash
helm show values oci://ghcr.io/securo-finance/charts/securo --version 0.14.0
```

## Upgrading

```bash
helm upgrade securo oci://ghcr.io/securo-finance/charts/securo --version <NEW_VERSION>
```

Every install and upgrade runs a migration Job with the new image, and the backend, worker, beat and MCP server pods wait in `Init` until the database reaches that image's schema, while the old pods keep serving. Give `helm upgrade --wait` a `--timeout` longer than the migration takes. Back up your database before upgrading, as with any deployment method. Details in [Database Migrations](/docs/deployment/kubernetes-prod#7-database-migrations).

Upgrading to 0.20.0 with `mcpServer.enabled: true`: `/mcp` is no longer routed by that setting alone. Set `mcpServer.publicRoute: true` and point `config.agentsExternalMcpUrl` at the public URL, or external MCP clients get a 404 after the upgrade. The [Docker guide](/docs/deployment/docker#updating-to-v0200) lists the other changes of that version (the generated `SECRET_KEY` and the MCP tokens to create again).

## Production Deployments

For production clusters requiring external PostgreSQL (`pgvector`), external Redis, secrets management via `existingSecret`, automated Ingress / Gateway API TLS with `cert-manager`, and horizontal pod autoscaling, see the **[Kubernetes (Helm) Production](/docs/deployment/kubernetes-prod)** guide.
