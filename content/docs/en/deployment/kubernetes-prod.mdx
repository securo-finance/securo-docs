description: Deploy Securo securely to a production Kubernetes cluster with external databases, secrets management, Ingress/TLS, and autoscaling.
---

When deploying Securo to a production Kubernetes cluster, we strongly recommend bypassing plain-text secrets in `values.yaml` in favor of external secret management, using managed or clustered databases, configuring automated TLS with Ingress or the Gateway API, and enabling autoscaling.

For a local testing or general overview of the Helm chart, see the [Kubernetes (Helm)](/docs/deployment/kubernetes) guide first.

## 1. Secrets Management (`existingSecret`)

In production, avoid placing sensitive credentials (like `SECRET_KEY`, database credentials, or API keys) directly in your `values.yaml` or Git repository. Instead, create a Kubernetes `Secret` out-of-band or manage it using tools like **External Secrets Operator**, **Sealed Secrets**, or **HashiCorp Vault**.

### Create the Secret
Create a `securo-secrets.yaml` containing your production credentials:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: securo-secrets
  namespace: default
type: Opaque
stringData:
  SECRET_KEY: "your-strong-random-secret-key"   # optional: left out, Securo generates one and keeps it in the database
  DATABASE_URL: "postgresql+asyncpg://securo_user:strong_password@postgres-ha.database.svc.cluster.local:5432/securo"
  # Optional integrations
  PLUGGY_CLIENT_ID: "your-pluggy-client-id"
  PLUGGY_CLIENT_SECRET: "your-pluggy-client-secret"
  OPENEXCHANGERATES_APP_ID: "your-openexchangerates-app-id"
  AGENTS_OPENAI_API_KEY: "your-openai-api-key"
```

Apply it to your cluster:

```bash
kubectl apply -f securo-secrets.yaml
```

### Pass the Secret to Helm
Tell the Helm release to consume your existing secret:

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.existingSecret=securo-secrets \
  --set global.domain=securo.yourdomain.com
```

## 2. External Databases (PostgreSQL & Redis)

By default, the chart deploys bundled single-instance StatefulSets for PostgreSQL and Redis. For production high availability and backup management, disable the internal databases and connect Securo to managed cloud services (e.g. AWS RDS / ElastiCache, GCP Cloud SQL / Memorystore) or HA in-cluster operators.

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set postgresql.enabled=false \
  --set redis.enabled=false \
  --set config.redisUrl="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set config.celeryBrokerUrl="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set config.celeryResultBackend="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set global.existingSecret=securo-secrets \
  --set global.domain=securo.yourdomain.com
```

*(Ensure `DATABASE_URL` is defined inside your `securo-secrets` secret).*

<Callout type="warn">
### PostgreSQL `pgvector` Requirement

Securo relies on the `pgvector` extension for vector embeddings, financial agents, and semantic document search. Your external PostgreSQL database **must** have the `pgvector` extension installed. Run the following in your database before starting Securo:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```
</Callout>

<Callout>
### Redis Architecture Note

Securo connects to a single Redis endpoint for caching, rate limiting, and Celery task brokering. Standalone Redis instances or setups exposed through a single endpoint/proxy (such as AWS ElastiCache with Cluster Mode disabled) are supported. **Redis Sentinel and Redis Cluster (multi-shard mode) are not supported.**
</Callout>

### Client Certificates, Private CAs and Extra Settings

`backend`, `celeryWorker`, `celeryBeat`, `migration` and `mcpServer` each take `extraEnv`, `extraEnvFrom`, `extraVolumes` and `extraVolumeMounts`, empty by default and written in the usual Kubernetes shapes. `extraEnv` is read after the chart's ConfigMap and Secret, so it wins over both. Give the migration Job the same extras as the pods: it reaches the database first. Each pod's `wait-for-schema` init container takes that pod's own extras, so it reaches the database the same way.

For example, a PostgreSQL that authenticates with a TLS client certificate:

```yaml
# values-production.yaml
backend:
  extraEnv:
    - name: PGSSLMODE
      value: verify-full
    - name: PGSSLCERT
      value: /etc/pg-tls/tls.crt
    - name: PGSSLKEY
      value: /etc/pg-tls/tls.key
    - name: PGSSLROOTCERT
      value: /etc/pg-tls/ca.crt
  extraVolumes:
    - name: pg-client-tls
      secret:
        secretName: pg-client-tls
  extraVolumeMounts:
    - name: pg-client-tls
      mountPath: /etc/pg-tls
      readOnly: true
```

Repeat the block under `celeryWorker`, `celeryBeat` and `migration`, since they connect to the same database, and under `mcpServer` when the AI agents and the MCP server are on: it opens its own database sessions for the agents' tools.

To mount a PersistentVolumeClaim you already have for attachments, set `persistence.attachments.existingClaim` to its name and keep `persistence.attachments.enabled: true`; the chart then creates no claim of its own and leaves yours alone on uninstall.

<Callout type="warn">
On a release that is already running, don't switch to `existingClaim` in a single upgrade: the chart's own claim leaves the release, Helm deletes it, and with a `Delete` reclaim policy your attachments go with it. Do it in two steps: annotate the chart's PVC with `helm.sh/resource-policy: keep` and upgrade, then set `existingClaim` and upgrade again. A claim you created yourself, outside the release, needs no handoff.
</Callout>

## 3. High Availability and Storage

### Shared Storage (`ReadWriteMany` / RWX)

By default, the Helm chart enables a PersistentVolumeClaim for file attachments (`persistence.attachments.enabled=true`) using `ReadWriteOnce` (RWO) storage.

Attachment files (as well as agent knowledge files and embedding models if the AI agents feature is enabled) are shared concurrently across the **Backend**, **Celery Worker**, and **MCP Server** pods.

If your pods are scheduled across multiple worker nodes, you must configure a storage class that supports `ReadWriteMany` (RWX) access mode (such as NFS, CephFS, AWS EFS, or GCP Filestore):

```yaml
# values-production.yaml
persistence:
  attachments:
    enabled: true
    storageClass: "nfs-client" # e.g. efs-sc, cephfs, or your RWX storage class
    accessMode: ReadWriteMany
    size: 10Gi
  agentKnowledge:
    enabled: true
    storageClass: "nfs-client"
    accessMode: ReadWriteMany
    size: 10Gi
```

<Callout type="warn">
`ReadWriteOnce` (RWO) storage only works if all pods mounting the volume are scheduled onto the same single node.
</Callout>

### Managed Backups

The in-app [managed backups](/docs/deployment/docker#managed-backups-in-the-app) need a volume of their own, and it is off by default. Turn it on with `persistence.backups.enabled: true` (5Gi, `ReadWriteOnce` unless you change `accessMode` and `storageClass`); the Backend, Celery Worker and Celery Beat pods then mount it at `/app/data/backups`, under the same RWX rule as above. Without it, backups run on the server live on pod-local storage and are lost when the pod is replaced, and scheduled backups are turned off because the API and the worker don't share a filesystem. Downloading a backup straight from the page works either way.

### S3-Compatible Object Storage

Instead of an RWX volume for attachments, Securo can keep them in an S3-compatible bucket (AWS S3, MinIO, Garage and others). Create a private bucket, then:

```yaml
# values-production.yaml
config:
  storageProvider: "s3"
  storageS3Bucket: "securo-attachments"
  storageS3Region: "us-east-1"
  storageS3EndpointUrl: ""          # empty for AWS S3; your endpoint for MinIO or Garage
  storageS3AddressingStyle: "auto"  # use path for Garage/MinIO
persistence:
  attachments:
    enabled: false
```

Put `STORAGE_S3_ACCESS_KEY` and `STORAGE_S3_SECRET_KEY` in your `existingSecret` (or `secret.storageS3AccessKey` and `secret.storageS3SecretKey`). Leave both out to use the SDK's credential chain, such as an IAM role for the service account. Invoice attachments and logos go to the bucket too; agent knowledge files and embedding models still need their volumes when agents are on.

<Callout type="warn">
Copy the files already in the attachments volume to the bucket before you disable that PVC, using each file's path inside the volume as its object key.
</Callout>

### Singleton Celery Beat Scheduler

While Backend and Celery Worker pods scale horizontally, **Celery Beat must run as a strict singleton** (exactly 1 replica) to prevent duplicate background scheduling (such as duplicate bank sync jobs). The Helm chart automatically enforces this constraint.

### Plugins With Code

Data plugins (categories, rules, themes) only need `config.pluginsEnabled: "true"`. [Plugins with code](/docs/features/plugins#plugins-with-code) also need the plugin runner and its egress proxy, which the chart creates:

```yaml
# values-production.yaml
config:
  pluginsEnabled: "true"

plugins:
  runner:
    enabled: true
```

- **Credentials**: the chart generates a Secret with a random runner token and egress secret, kept across upgrades. To bring your own, set `plugins.runner.existingSecret` to a Secret with `PLUGINS_RUNNER_TOKEN` and `PLUGINS_EGRESS_SECRET`, each at least 32 characters, or set `plugins.runner.token` and `plugins.runner.egressSecret`. To rotate, set new values for those two: the pods roll together. With a Secret of your own, restart the runner StatefulSet and the egress, backend, worker and beat Deployments after changing it
- **GitOps**: under Argo CD, Flux or plain `helm template`, the chart can't read the existing Secret, so every sync would generate a new pair. Manage the Secret yourself there (`existingSecret`) or set fixed values
- **Existing releases**: turn the runner on with `helm upgrade --reset-then-reuse-values` (Helm 3.14+). `--reuse-values --set plugins.runner.enabled=true` leaves the rest of `plugins.runner` unset and the render stops; on older Helm, pass a values file with every override the release already has
- **Pod Security**: the runner runs as root so it can give each plugin its own user, so its namespace needs the `baseline` Pod Security Standard or looser
- **One replica**: the runner is a one-replica StatefulSet, and the chart refuses more. Its volume keeps the installed plugin code and survives turning the runner off
- **Network**: a NetworkPolicy, on by default, lets the runner reach only the backend, the worker, beat, DNS and the egress proxy. Keep it on unless your CNI doesn't enforce `NetworkPolicy`. If your cluster resolves through an address the policy can't match (a NodeLocal DNSCache at `169.254.20.10`, say), list it in `plugins.networkPolicy.dnsCIDRs`

Plugin code reaches the internet only through the egress proxy, which allows the hosts each plugin declared and refuses private addresses. DNS is the exception: plugin code can send queries to the cluster resolver.

## 4. Working Ingress + cert-manager Example

Securo routes all API traffic through the frontend container internally, so your Ingress controller only needs to expose the root path (`/`) to the frontend service.

### Step 1: Set up cert-manager ClusterIssuer
If you use [cert-manager](https://cert-manager.io/), create a production Let's Encrypt `ClusterIssuer`:

```yaml
# cluster-issuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@yourdomain.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: nginx
```

```bash
kubectl apply -f cluster-issuer.yaml
```

### Step 2: Deploy Securo with Ingress & TLS

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.domain=securo.yourdomain.com \
  --set global.tls=true \
  --set ingress.enabled=true \
  --set ingress.className=nginx \
  --set ingress.annotations."cert-manager\.io/cluster-issuer"=letsencrypt-prod \
  --set ingress.tls[0].secretName=securo-tls-cert \
  --set "ingress.tls[0].hosts[0]=securo.yourdomain.com" \
  --set global.existingSecret=securo-secrets
```

## 5. Gateway API Alternative (`HTTPRoute`)

If your cluster uses the modern Kubernetes [Gateway API](https://gateway-api.sigs.k8s.io/) (e.g., with Cilium, Envoy Gateway, or Istio), you can configure an `HTTPRoute` instead of an Ingress.

### Step 1: Configure Gateway Resource with TLS
Create a `Gateway` configured with `cert-manager` for automated certificate issuance:

```yaml
# gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: external-gateway
  namespace: default
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  gatewayClassName: cilium # or your gateway class
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "securo.yourdomain.com"
      tls:
        mode: Terminate
        certificateRefs:
          - name: securo-gateway-tls
```

```bash
kubectl apply -f gateway.yaml
```

### Step 2: Deploy Securo with `HTTPRoute`

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.domain=securo.yourdomain.com \
  --set global.tls=true \
  --set ingress.enabled=false \
  --set httpRoute.enabled=true \
  --set "httpRoute.parentRefs[0].name=external-gateway" \
  --set "httpRoute.parentRefs[0].namespace=default" \
  --set global.existingSecret=securo-secrets
```

## 6. Horizontal Pod Autoscaling (HPA)

To handle production traffic spikes dynamically, enable Horizontal Pod Autoscaling. The Helm chart provisions `HorizontalPodAutoscaler` resources for all scalable components (Frontend, Backend, Celery Worker, and MCP Server), while keeping the Celery Beat scheduler as a single instance.

<Callout>
HPA requires a `metrics-server` installed in your cluster (e.g. via `kube-prometheus-stack` or standalone `metrics-server`).
</Callout>

### Enable HPA in `values-production.yaml`

```yaml
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 80
  targetMemoryUtilizationPercentage: 80
```

Deploy with autoscaling enabled:

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  -f values-production.yaml
```

## 7. Database Migrations

Every install and upgrade creates a migration Job that runs `alembic upgrade head` with the release's new image and configuration. The backend, Celery worker, Celery beat and MCP server pods start with a `wait-for-schema` init container that checks the database every 5 seconds and lets the pod start only once it is at the migration head of the pod's image.

- **First install**: the Job retries until the database accepts connections, so the bundled PostgreSQL can come up next to it. The other pods stay in `Init` until the Job finishes
- **Upgrade**: the new pods stay in `Init` until the database reaches the new image's head, and the Deployments keep the old pods serving until then. A migration that rewrites a large table keeps them there for as long as it takes, so give `helm upgrade --wait` a `--timeout` above that
- **Following it**: each upgrade gets a fresh Job, named after its pod template and the release revision, and Helm deletes the previous one. Read its output with `kubectl logs job/<name>`
- **When it fails**: the new pods stay in `Init` and the old ones keep serving. Fix the cause and run `helm upgrade` again
- **Going back**: an older image does not downgrade the database, so its pods stay in `Init`. Restore the backup you took before the upgrade, or stay on the newer version

Before this change the Job was a `post-install` and `post-upgrade` hook, which Helm runs only after the new pods are ready: each upgrade with a schema change served the new code against the old schema until the Job finished.

## 8. Upgrading in Production

To upgrade an existing production deployment to a new release:

```bash
# 1. Always back up your external database first
pg_dump -U securo_user -h postgres-ha -d securo > securo-pre-upgrade-$(date +%Y%m%d).sql

# 2. Upgrade the Helm release
helm upgrade securo oci://ghcr.io/securo-finance/charts/securo \
  --version <NEW_VERSION> \
  -f values-production.yaml
```
