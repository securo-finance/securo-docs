---

Ao levar o Securo para um cluster Kubernetes de produção, recomendamos fortemente não deixar segredos em texto puro no `values.yaml`, e sim usar gestão externa de segredos, bancos gerenciados ou em cluster, TLS automatizado com Ingress ou Gateway API, e autoscaling habilitado.

Para testes locais ou uma visão geral do Helm chart, veja antes o guia [Kubernetes (Helm)](/pt-BR/docs/deployment/kubernetes).

## 1. Gestão de Segredos (`existingSecret`)

Em produção, evite colocar credenciais sensíveis (como `SECRET_KEY`, credenciais do banco ou chaves de API) direto no `values.yaml` ou no repositório Git. Em vez disso, crie um `Secret` do Kubernetes por fora, ou gerencie com ferramentas como **External Secrets Operator**, **Sealed Secrets** ou **HashiCorp Vault**.

### Crie o Secret
Crie um `securo-secrets.yaml` com as credenciais de produção:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: securo-secrets
  namespace: default
type: Opaque
stringData:
  SECRET_KEY: "sua-chave-secreta-aleatoria-e-forte"   # opcional: sem ela, o Securo gera uma e a guarda no banco
  DATABASE_URL: "postgresql+asyncpg://securo_user:senha_forte@postgres-ha.database.svc.cluster.local:5432/securo"
  # Integrações opcionais
  PLUGGY_CLIENT_ID: "seu-pluggy-client-id"
  PLUGGY_CLIENT_SECRET: "seu-pluggy-client-secret"
  OPENEXCHANGERATES_APP_ID: "seu-openexchangerates-app-id"
  AGENTS_OPENAI_API_KEY: "sua-chave-de-api-da-openai"
```

Aplique no cluster:

```bash
kubectl apply -f securo-secrets.yaml
```

### Passe o Secret para o Helm
Diga ao release do Helm para consumir o secret existente:

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.existingSecret=securo-secrets \
  --set global.domain=securo.seudominio.com
```

## 2. Bancos Externos (PostgreSQL e Redis)

Por padrão, o chart sobe StatefulSets de instância única para PostgreSQL e Redis. Para alta disponibilidade e gestão de backup em produção, desabilite os bancos internos e conecte o Securo a serviços gerenciados na nuvem (por exemplo AWS RDS / ElastiCache, GCP Cloud SQL / Memorystore) ou a operadores de alta disponibilidade dentro do cluster.

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set postgresql.enabled=false \
  --set redis.enabled=false \
  --set config.redisUrl="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set config.celeryBrokerUrl="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set config.celeryResultBackend="redis://redis-ha.database.svc.cluster.local:6379/0" \
  --set global.existingSecret=securo-secrets \
  --set global.domain=securo.seudominio.com
```

*(Garanta que `DATABASE_URL` esteja definida dentro do seu secret `securo-secrets`.)*

<Callout type="warn">
### Requisito do `pgvector` no PostgreSQL

O Securo depende da extensão `pgvector` para embeddings vetoriais, agentes financeiros e busca semântica em documentos. O seu PostgreSQL externo **precisa** ter a extensão `pgvector` instalada. Rode o comando abaixo no banco antes de subir o Securo:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```
</Callout>

<Callout>
### Nota sobre a Arquitetura do Redis

O Securo se conecta a um único endpoint Redis para cache, rate limiting e broker de tasks do Celery. Instâncias Redis standalone ou expostas por um único endpoint/proxy (como o AWS ElastiCache com Cluster Mode desabilitado) são suportadas. **Redis Sentinel e Redis Cluster (modo multi-shard) não são suportados.**
</Callout>

### Certificados de Cliente, CAs Privadas e Configurações Extras

`backend`, `celeryWorker`, `celeryBeat`, `migration` e `mcpServer` aceitam `extraEnv`, `extraEnvFrom`, `extraVolumes` e `extraVolumeMounts`, vazios por padrão e escritos nos formatos de sempre do Kubernetes. O `extraEnv` é lido depois do ConfigMap e do Secret do chart, então prevalece sobre os dois. Dê ao Job de migração os mesmos extras dos pods: ele chega ao banco primeiro. O init container `wait-for-schema` de cada pod usa os extras do próprio pod, então chega ao banco do mesmo jeito.

Por exemplo, um PostgreSQL que autentica com certificado de cliente TLS:

```yaml
# values-production.yaml
backend:
  extraEnv:
    - name: PGSSLMODE
      value: verify-full
    - name: PGSSLCERT
      value: /etc/pg-tls/tls.crt
    - name: PGSSLKEY
      value: /etc/pg-tls/tls.key
    - name: PGSSLROOTCERT
      value: /etc/pg-tls/ca.crt
  extraVolumes:
    - name: pg-client-tls
      secret:
        secretName: pg-client-tls
  extraVolumeMounts:
    - name: pg-client-tls
      mountPath: /etc/pg-tls
      readOnly: true
```

Repita o bloco em `celeryWorker`, `celeryBeat` e `migration`, que se conectam ao mesmo banco, e em `mcpServer` quando os agentes de IA e o servidor MCP estão ligados: ele abre as próprias sessões no banco para as ferramentas dos agentes.

Para montar um PersistentVolumeClaim que você já tem para os anexos, informe o nome dele em `persistence.attachments.existingClaim` e mantenha `persistence.attachments.enabled: true`; o chart deixa de criar o próprio claim e não mexe no seu ao desinstalar.

<Callout type="warn">
Numa release que já está rodando, não troque para `existingClaim` num único upgrade: o claim do próprio chart sai da release, o Helm o apaga e, com reclaim policy `Delete`, os anexos vão junto. Faça em dois passos: anote o PVC do chart com `helm.sh/resource-policy: keep` e faça o upgrade, depois defina `existingClaim` e faça outro upgrade. Um claim que você criou por fora da release não precisa dessa troca.
</Callout>

## 3. Alta Disponibilidade e Armazenamento

### Armazenamento Compartilhado (`ReadWriteMany` / RWX)

Por padrão, o Helm chart habilita um PersistentVolumeClaim para anexos (`persistence.attachments.enabled=true`) usando armazenamento `ReadWriteOnce` (RWO).

Os arquivos de anexo (assim como os arquivos da base de conhecimento dos agentes e os modelos de embedding, se o recurso de agentes de IA estiver habilitado) são compartilhados simultaneamente entre os pods do **Backend**, do **Celery Worker** e do **MCP Server**.

Se os seus pods forem agendados em nós diferentes, você precisa configurar uma storage class que suporte o modo de acesso `ReadWriteMany` (RWX), como NFS, CephFS, AWS EFS ou GCP Filestore:

```yaml
# values-production.yaml
persistence:
  attachments:
    enabled: true
    storageClass: "nfs-client" # ex.: efs-sc, cephfs, ou a sua storage class RWX
    accessMode: ReadWriteMany
    size: 10Gi
  agentKnowledge:
    enabled: true
    storageClass: "nfs-client"
    accessMode: ReadWriteMany
    size: 10Gi
```

<Callout type="warn">
Armazenamento `ReadWriteOnce` (RWO) só funciona se todos os pods que montam o volume forem agendados no mesmo nó.
</Callout>

### Backups Gerenciados

Os [backups gerenciados](/pt-BR/docs/deployment/docker#backups-gerenciados-no-app) do app precisam de um volume próprio, que vem desligado. Ligue com `persistence.backups.enabled: true` (5Gi, `ReadWriteOnce` a menos que você mude `accessMode` e `storageClass`); os pods do Backend, do Celery Worker e do Celery Beat passam a montá-lo em `/app/data/backups`, com a mesma regra de RWX acima. Sem ele, os backups executados no servidor ficam no armazenamento local do pod e se perdem quando o pod é substituído, e os backups agendados ficam desligados porque a API e o worker não dividem um sistema de arquivos. Baixar um backup direto da página funciona dos dois jeitos.

### Armazenamento de Objetos Compatível com S3

Em vez de um volume RWX para os anexos, o Securo pode guardá-los num bucket compatível com S3 (AWS S3, MinIO, Garage e outros). Crie um bucket privado e então:

```yaml
# values-production.yaml
config:
  storageProvider: "s3"
  storageS3Bucket: "securo-attachments"
  storageS3Region: "us-east-1"
  storageS3EndpointUrl: ""          # vazio no AWS S3; o seu endpoint no MinIO ou Garage
  storageS3AddressingStyle: "auto"  # use path no Garage/MinIO
persistence:
  attachments:
    enabled: false
```

Coloque `STORAGE_S3_ACCESS_KEY` e `STORAGE_S3_SECRET_KEY` no seu `existingSecret` (ou em `secret.storageS3AccessKey` e `secret.storageS3SecretKey`). Deixe as duas de fora para usar a cadeia de credenciais do SDK, como um papel IAM da service account. Os anexos e logos de faturas também vão para o bucket; os arquivos de conhecimento dos agentes e os modelos de embedding continuam precisando dos volumes deles quando os agentes estão ligados.

<Callout type="warn">
Copie para o bucket os arquivos que já estão no volume de anexos antes de desabilitar esse PVC, usando o caminho de cada arquivo dentro do volume como a chave do objeto.
</Callout>

### Celery Beat como Instância Única

Enquanto os pods de Backend e de Celery Worker escalam horizontalmente, o **Celery Beat precisa rodar como instância única** (exatamente 1 réplica) para evitar agendamentos duplicados em segundo plano, como jobs repetidos de sincronização bancária. O Helm chart aplica essa restrição automaticamente.

### Plugins com Código

Plugins de dados (categorias, regras, temas) só precisam de `config.pluginsEnabled: "true"`. [Plugins com código](/pt-BR/docs/features/plugins#plugins-com-código) também precisam do runner de plugins e do proxy de saída dele, que o chart cria:

```yaml
# values-production.yaml
config:
  pluginsEnabled: "true"

plugins:
  runner:
    enabled: true
```

- **Credenciais**: o chart gera um Secret com um token do runner e um segredo de saída aleatórios, mantidos entre atualizações. Para usar os seus, aponte `plugins.runner.existingSecret` para um Secret com `PLUGINS_RUNNER_TOKEN` e `PLUGINS_EGRESS_SECRET`, cada um com pelo menos 32 caracteres, ou defina `plugins.runner.token` e `plugins.runner.egressSecret`. Para trocar, defina valores novos para esses dois: os pods reiniciam juntos. Com um Secret seu, reinicie o StatefulSet do runner e os Deployments do proxy de saída, do backend, do worker e do beat depois de mudá-lo
- **GitOps**: no Argo CD, no Flux ou com `helm template` puro, o chart não consegue ler o Secret que já existe, então cada sync geraria um par novo. Nesses casos, gerencie o Secret você mesmo (`existingSecret`) ou defina valores fixos
- **Releases que já existem**: ligue o runner com `helm upgrade --reset-then-reuse-values` (Helm 3.14+). `--reuse-values --set plugins.runner.enabled=true` deixa o resto de `plugins.runner` sem valor e a renderização para; em versões mais antigas do Helm, passe um arquivo de values com todas as sobrescritas que a release já tem
- **Pod Security**: o runner roda como root para dar a cada plugin um usuário próprio, então o namespace dele precisa do Pod Security Standard `baseline` ou mais permissivo
- **Uma réplica**: o runner é um StatefulSet de uma réplica, e o chart recusa mais que isso. O volume dele guarda o código dos plugins instalados e sobrevive a desligar o runner
- **Rede**: uma NetworkPolicy, ligada por padrão, deixa o runner falar só com o backend, o worker, o beat, o DNS e o proxy de saída. Mantenha ligada, a não ser que o seu CNI não aplique `NetworkPolicy`. Se o cluster resolve nomes por um endereço que a política não alcança (um NodeLocal DNSCache em `169.254.20.10`, por exemplo), liste-o em `plugins.networkPolicy.dnsCIDRs`

O código dos plugins só chega à internet pelo proxy de saída, que libera os hosts que cada plugin declarou e recusa endereços privados. O DNS é a exceção: o código pode mandar consultas ao resolvedor do cluster.

## 4. Exemplo Funcional de Ingress + cert-manager

O Securo roteia todo o tráfego de API pelo contêiner do frontend internamente, então o seu controlador de Ingress só precisa expor o caminho raiz (`/`) para o serviço de frontend.

### Passo 1: Configure o ClusterIssuer do cert-manager
Se você usa o [cert-manager](https://cert-manager.io/), crie um `ClusterIssuer` de produção do Let's Encrypt:

```yaml
# cluster-issuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@seudominio.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: nginx
```

```bash
kubectl apply -f cluster-issuer.yaml
```

### Passo 2: Faça o deploy do Securo com Ingress e TLS

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.domain=securo.seudominio.com \
  --set global.tls=true \
  --set ingress.enabled=true \
  --set ingress.className=nginx \
  --set ingress.annotations."cert-manager\.io/cluster-issuer"=letsencrypt-prod \
  --set ingress.tls[0].secretName=securo-tls-cert \
  --set "ingress.tls[0].hosts[0]=securo.seudominio.com" \
  --set global.existingSecret=securo-secrets
```

## 5. Alternativa com Gateway API (`HTTPRoute`)

Se o seu cluster usa a [Gateway API](https://gateway-api.sigs.k8s.io/) moderna do Kubernetes (por exemplo com Cilium, Envoy Gateway ou Istio), você pode configurar um `HTTPRoute` no lugar de um Ingress.

### Passo 1: Configure o recurso Gateway com TLS
Crie um `Gateway` configurado com o `cert-manager` para emissão automática de certificados:

```yaml
# gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: external-gateway
  namespace: default
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  gatewayClassName: cilium # ou a sua gateway class
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "securo.seudominio.com"
      tls:
        mode: Terminate
        certificateRefs:
          - name: securo-gateway-tls
```

```bash
kubectl apply -f gateway.yaml
```

### Passo 2: Faça o deploy do Securo com `HTTPRoute`

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  --set global.domain=securo.seudominio.com \
  --set global.tls=true \
  --set ingress.enabled=false \
  --set httpRoute.enabled=true \
  --set "httpRoute.parentRefs[0].name=external-gateway" \
  --set "httpRoute.parentRefs[0].namespace=default" \
  --set global.existingSecret=securo-secrets
```

## 6. Horizontal Pod Autoscaling (HPA)

Para lidar com picos de tráfego em produção de forma dinâmica, habilite o Horizontal Pod Autoscaling. O Helm chart cria recursos `HorizontalPodAutoscaler` para todos os componentes escaláveis (Frontend, Backend, Celery Worker e MCP Server), mantendo o agendador Celery Beat como instância única.

<Callout>
O HPA exige um `metrics-server` instalado no cluster (por exemplo via `kube-prometheus-stack` ou o `metrics-server` avulso).
</Callout>

### Habilite o HPA no `values-production.yaml`

```yaml
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 80
  targetMemoryUtilizationPercentage: 80
```

Faça o deploy com autoscaling habilitado:

```bash
helm install securo oci://ghcr.io/securo-finance/charts/securo \
  --version 0.14.0 \
  -f values-production.yaml
```

## 7. Migrações do Banco

Cada instalação e atualização cria um Job de migração que roda o `alembic upgrade head` com a imagem e a configuração novas da release. Os pods do backend, do Celery worker, do Celery beat e do servidor MCP começam com um init container `wait-for-schema`, que consulta o banco a cada 5 segundos e só deixa o pod subir quando ele está no head de migração da imagem do pod.

- **Primeira instalação**: o Job tenta de novo até o banco aceitar conexões, então o PostgreSQL embutido pode subir junto. Os outros pods ficam em `Init` até o Job terminar
- **Atualização**: os pods novos ficam em `Init` até o banco chegar ao head da imagem nova, e os Deployments mantêm os pods antigos atendendo até lá. Uma migração que reescreve uma tabela grande segura os pods ali pelo tempo que levar, então dê ao `helm upgrade --wait` um `--timeout` acima disso
- **Acompanhando**: cada atualização ganha um Job novo, com nome derivado do template do pod e da revisão da release, e o Helm apaga o anterior. Leia a saída com `kubectl logs job/<nome>`
- **Quando falha**: os pods novos ficam em `Init` e os antigos continuam atendendo. Corrija a causa e rode `helm upgrade` de novo
- **Voltando de versão**: uma imagem mais antiga não faz downgrade do banco, então os pods dela ficam em `Init`. Restaure o backup feito antes da atualização, ou fique na versão nova

Antes dessa mudança o Job era um hook de `post-install` e `post-upgrade`, que o Helm só roda depois que os pods novos ficam prontos: toda atualização com mudança de schema servia o código novo contra o schema antigo até o Job terminar.

## 8. Atualizando em Produção

Para atualizar um deploy de produção existente para uma nova release:

```bash
# 1. Sempre faça backup do seu banco externo primeiro
pg_dump -U securo_user -h postgres-ha -d securo > securo-pre-upgrade-$(date +%Y%m%d).sql

# 2. Atualize o release do Helm
helm upgrade securo oci://ghcr.io/securo-finance/charts/securo \
  --version <NOVA_VERSAO> \
  -f values-production.yaml
```
