Este guia cobre o deploy do Securo em um servidor de produção. Se você só está testando o Securo localmente, veja o [guia de Instalação](/pt-BR/docs/getting-started/installation).

## Produção vs Desenvolvimento

O Securo vem com dois arquivos Docker Compose:

| Arquivo                     | Caso de Uso     | Imagens                          |
| --------------------------- | --------------- | -------------------------------- |
| `docker-compose.yml`        | Desenvolvimento | Build do código, hot reload      |
| `docker-compose.prod.yml`   | Produção        | Imagens pré-buildadas do GHCR    |

Para produção, use sempre `docker-compose.prod.yml`. Ele puxa imagens otimizadas, já compiladas, do GitHub Container Registry, em vez de buildar a partir do código-fonte.

## Requisitos do Servidor

- Um servidor Linux (Ubuntu 22.04+ recomendado) com pelo menos **2 GB de RAM** (a stack roda seis containers)
- Docker Engine e o plugin Docker Compose instalados. Podman também funciona: use podman-compose **1.6.0 ou mais novo**, versões antigas quebram silenciosamente a interpolação de variáveis do compose, o que aparece como falhas de CORS e de callback de login
- Um nome de domínio (opcional, mas recomendado para HTTPS)

> O caminho mais rápido num servidor novo é o instalador de uma linha, que faz tudo das próximas duas seções por você (incluindo instalar o Docker e gerar o `.env`): `curl -fsSL https://usesecuro.com/install.sh | bash`

## Passos de Deploy

### 1. Instale o Docker

No seu servidor, instale o Docker usando o script oficial:

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
```

Faça logout e login novamente para a mudança de grupo entrar em vigor.

### 2. Clone e Configure

```bash
git clone https://github.com/securo-finance/securo.git
cd securo
```

Crie um arquivo `.env` com uma secret key forte:

```bash
echo "SECRET_KEY=$(openssl rand -hex 32)" > .env
```

Se você quiser sincronização bancária ou taxas de câmbio, adicione essas chaves também:

```ini
PLUGGY_CLIENT_ID=seu-client-id
PLUGGY_CLIENT_SECRET=seu-client-secret
OPENEXCHANGERATES_APP_ID=seu-app-id
```

### 3. Suba o Securo

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

Confira se todos os containers estão rodando:

```bash
docker compose -f docker-compose.prod.yml ps
```

## Defina FRONTEND_URL para Qualquer Acesso Fora do Localhost

Se o Securo vai ser acessado por qualquer endereço diferente de `http://localhost:3000` (um IP da rede local, um domínio, um túnel), defina `FRONTEND_URL` no `.env` com essa URL pública exata **antes** de as pessoas fazerem login:

```ini
FRONTEND_URL=http://192.168.1.50:3000
```

Essa única variável comanda o CORS, os callbacks OAuth da sincronização bancária, os redirects padrão do OIDC e as origens das passkeys. Pular esse passo é a causa mais comum dos relatos de "o login funciona no servidor mas não no meu notebook". Reinicie depois de mudar: `docker compose -f docker-compose.prod.yml up -d`

Para mudar as portas publicadas, defina `FRONTEND_PORT` e `BACKEND_PORT` no `.env`. Num servidor mais protegido, você pode tirar o backend da interface pública com `BACKEND_PORT=127.0.0.1:8000`; o frontend faz proxy de `/api` para o backend internamente, então nada de fora precisa da porta 8000.

## Configurando HTTPS

Para produção, você deve colocar o Securo atrás de um proxy reverso com TLS. Aqui está um exemplo mínimo usando **Caddy** (que cuida do HTTPS automaticamente):

```bash
# Instale o Caddy
sudo apt install -y caddy
```

Edite `/etc/caddy/Caddyfile`:

```text
securo.seudominio.com {
    reverse_proxy localhost:3000
}
```

Reinicie o Caddy:

```bash
sudo systemctl restart caddy
```

O Caddy obtém e renova automaticamente um certificado Let's Encrypt. Atualize o `.env` para refletir a URL pública:

```ini
FRONTEND_URL=https://securo.seudominio.com
```

Em seguida, reinicie o Securo: `docker compose -f docker-compose.prod.yml up -d`

## Backups

### Backup do Banco de Dados

Exporte o banco PostgreSQL para um arquivo SQL:

```bash
docker compose -f docker-compose.prod.yml exec db \
  pg_dump -U postgres securo > backup-$(date +%Y%m%d).sql
```

### Restauração do Banco

```bash
docker compose -f docker-compose.prod.yml exec -T db \
  psql -U postgres securo < backup-20260401.sql
```

### Anexos e Outros Volumes

O banco não é a história toda: os anexos de transações ficam no volume `attachments`, e a base de conhecimento dos agentes (se você habilitou o recurso opcional de IA) fica em `agent_knowledge`. Uma restauração só do banco perde silenciosamente todos os arquivos enviados, então faça backup desses volumes também:

```bash
docker run --rm -v securo_attachments:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/attachments-$(date +%Y%m%d).tar.gz -C /data .
```

Restaure extraindo para dentro do volume do mesmo jeito:

```bash
docker run --rm -v securo_attachments:/data -v "$(pwd)":/backup alpine \
  tar xzf /backup/attachments-20260401.tar.gz -C /data
```

### Backups Automatizados

Adicione um cron job para backups diários (o cron roda com um PATH mínimo, então use o caminho absoluto do docker):

```bash
crontab -e
```

```text
0 3 * * * cd /caminho/para/securo && /usr/bin/docker compose -f docker-compose.prod.yml exec -T db pg_dump -U postgres securo > /backups/securo-$(date +\%Y\%m\%d).sql
```

## Atualizando

Baixe as imagens mais recentes e reinicie:

```bash
cd /caminho/para/securo
git pull
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

As migrations do banco de dados rodam automaticamente na inicialização (`alembic upgrade head`), então mudanças de schema são aplicadas durante a atualização. Faça um backup do banco antes de atualizar, e confira a [página de releases](https://github.com/securo-finance/securo/releases) para as notas do que mudou.

## Monitoramento

Verifique os logs em busca de problemas:

```bash
# Todos os serviços
docker compose -f docker-compose.prod.yml logs -f

# Somente backend
docker compose -f docker-compose.prod.yml logs -f backend

# Últimas 100 linhas
docker compose -f docker-compose.prod.yml logs --tail 100
```

Verifique o endpoint de health:

```bash
curl http://localhost:8000/api/health
```

## Solução de Problemas

**Containers ficam reiniciando**: verifique os logs com `docker compose -f docker-compose.prod.yml logs backend`. Causas comuns: pouca RAM, conflitos de porta (resolva com `FRONTEND_PORT`/`BACKEND_PORT`) ou, no Podman, podman-compose mais antigo que 1.6.0.

**Erros de login ou CORS a partir de outra máquina**: `FRONTEND_URL` está ausente ou não bate com a URL no navegador. Veja a seção acima.

**Conexão com o banco recusada**: o container do banco pode ainda não estar pronto. Ele tem um health check, mas em servidores lentos pode demorar mais. Aguarde 30 segundos e tente de novo.

**Sem espaço em disco**: imagens e volumes do Docker podem consumir bastante espaço. Limpe imagens antigas com `docker system prune`.

**Permissão negada nos anexos**: o volume de anexos precisa ter permissão de escrita para o usuário do container. Verifique as permissões com `docker compose -f docker-compose.prod.yml exec backend ls -la /app/data/`.
